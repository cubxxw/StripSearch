# StripSearch：从人物搜索到持续阅读

设计调研与提案，2026-09-23—24。状态：**推荐方案，尚未经用户选择或真实用户验证**。

[可视方案对照](board.html) · [A 首页](index.html#/home) · [A 手机阅读](index.html#/feed) · [B 发现集](board.html) · [验证记录](VALIDATION.md)

本次全部人物、帖子、讨论与 AI 回答为原创合成内容。原型独立于 `apps/web` 与此前 Signal Atlas；未改变现有产品功能、研究报告契约或开发里程碑。

## 1. 先改产品的重心

建议主张：**找到值得读的人，把他的公开创作读深。**

第一次到访，用户只需要输入名字。后续回来，用户应该直接看自己关注的人的更新，而不是重复面对搜索框。Web 负责低门槛发现和深入查证；iOS 负责随身阅读、接着上次追问、留下有价值的内容。两端共享人物、来源、内容与阅读位置。

主要使用时刻：

- 刚看到一篇有意思的文章，想知道作者还有什么值得读。
- 准备采访或交流，需要快速理解一个人的作品、长期关注点与近期变化。
- 通勤或睡前，想读自己挑选的人的新内容，顺手把一个问题想深。

本产品可能形成的差异，是**人物归属 + 跨平台内容整理 + 连续阅读 + 有出处的追问**组成一条完整路径。它是待验证的产品命题，不能仅凭设计宣称优于已有产品。

### 当前界面的问题与值得保留的部分

已实际查看当前 Signal Atlas 的桌面/手机首屏、账号图谱、研究流程，并点击独立候选查看归属变化。

- 值得保留：名字入口明确；同名不合并；出处与归属依据可展开；工作台具备研究控制能力。
- 问题：首次输入前就出现四种检索模式、配置入口和完整图谱；用户要先理解工具，才能开始理解人。
- 深色荧光界面强调「正在运行的研究系统」，与日常阅读和内容消费距离较大。
- 手机缺少以帖子为基本单位的阅读节奏，也没有「我上次读到哪里、还想知道什么」的持续体验。

## 2. Open Design：具体选什么

本机安装包的设计系统目录实际枚举到 **152 个 manifest**，目录 README 写 151，采用实际文件计数。对 12 个相关系统做了定向初筛，对下列候选阅读规则；打开并截图了 4 个成品模板示例。这里的品牌系统是 Open Design 整理的灵感包，不是品牌官方 SDK，也不等于其当前 App 的精确复刻。

### 推荐的组合

| 层次 | Open Design 名称 / ID | 采用什么 | 必须调整什么 |
|---|---|---|---|
| 主视觉底盘 | **Notion / `notion`** | 内容优先、暖中性色、弱分隔、清晰的文字层级 | 不继承企业官网的营销段落、指标卡、复杂导航 |
| 手机结构起点 | **Mobile App / `mobile-app`** | Feed、Detail、Profile 原型骨架；设备框与安全区域示意 | 适配完整流程；放大中文正文与触控区域；不复制示例的专注计时器内容 |
| Web 搜索页起点 | **Editorial Minimalism / `web-prototype-taste-editorial`** | 安静的画布、衬线标题与系统正文的关系 | 删除悬浮胶囊导航、Bento、价格区；按本项目需求改成名字输入优先 |
| 排版参考 | **kami（紙 / 纸）/ `kami`** | 中日文排版意识、节奏、低色彩噪声 | 不照搬全衬线、14px 正文、印刷行距和无动态约束；原包本来就不是 App UI |
| 内容浏览交互 | **Xiaohongshu / `xiaohongshu`** | 内容自身承载颜色、轻量作者行、卡片展开、移动底部面板 | 双列只用于「发现」；阅读默认单列；不以赞数为质量、不套品牌红与字标 |

**如果只能选一个设计系统：选 Notion。** 如果只能选一个移动原型模板：选 Mobile App。独特性要由人物聚合与原文追问产生，不能依赖把几个品牌的颜色拼在一起。

### 其他候选为何不做主模板

| 候选 | 调研判断 |
|---|---|
| `kami-landing` | 印刷文档与白皮书结构很完整，但无 JS 动效、全衬线和章节化内容不适合持续消费平台；适合导出的长报告 |
| `warm-editorial` | 适合长篇阅读；大标题、杂志章节和暖色容易让产品退回静态文章站 |
| `web-prototype-taste-soft` | 柔和按钮反馈可借用；双层容器、厚圆角和悬浮导航会增加阅读界面的视觉重量 |
| `paper` / `spacious` / `minimal` | 名称贴近需求，但规则较通用；不足以单独产生可识别的产品体验 |
| `editorial` / `publication` | 可作为排版素材；实际字体与色板并非都符合「日式克制」，不能只看名称选择 |
| `atelier-zero` | 杂志艺术指导明确，但拼贴、巨型字、罗马数字会抢走人物与原始内容的注意力 |
| `perplexity` | 借搜索、答案与出处的相邻关系；本地包偏研究终端，不作为消费端视觉底盘 |
| `apple` | 本地包参考的是 Apple Web 产品展示，不是原生 iOS HIG；不能用来宣称原生适配完成 |
| `social-media-dashboard` / `social-media-matrix-tracker-template` | 面向运营者的指标看板，与读者的目标不同；粉丝趋势与 KPI 不进入阅读首页 |
| `mobile-onboarding` / `wireframe-mobile-flow` | 可用来梳理流程；不采用前三屏介绍产品后才允许输入名字的引导 |

本轮没有安装或付费购买模板。Open Design 原生 UI 读取两次超时，捆绑 CLI 还报告 `@open-design/sidecar` 缺失。研究随后使用其实际安装文件与本地浏览器预览；**没有宣称已在 Open Design 窗口中创建新项目**。

## 3. 参考产品：借机制，而非借整套外观

1. **Notion：内容的间距关系。** 其 2026 年页面设计文章说明，以相邻内容的关系调整间距：段落有呼吸，连续列表保持紧凑。对应本产品：原文段落宽松，作者/来源/时间聚合成紧凑一组。[官方设计说明](https://www.notion.com/en-gb/blog/updating-the-design-of-notion-pages)
2. **小红书：先看内容，再进入细节。** 用本地 Xiaohongshu 包研究封面、作者行、双列发现与底部面板；这些是参考机制，不视作当前原生客户端实测。[官方 App Store 页面](https://apps.apple.com/cn/app/id741292507)
3. **Tapestry：聚合与时间序可以独立成立。** 官方产品使用统一时间线、时间顺序、过滤规则与阅读位置同步。借其透明排序与阅读连续性；人物归属和 AI 解释需要本产品另外解决。[官方产品](https://usetapestry.com/)
4. **Readwise Reader：AI 就在阅读上下文里。** 官方文档支持阅读、Feed、选段辅助；全库 Ghostreader 与手机单文档聊天还有平台差异。本设计借选段到解释再回原文的低摩擦路径。[Reader](https://readwise.io/read) · [Ghostreader 范围](https://docs.readwise.io/reader/guides/ghostreader/global)
5. **Are.na：探索来自连接。** 收藏的价值在于把材料连接到自己的问题，并沿连接继续探索。可借来设计「下一问」与相关材料，不需要强制猜测用户喜好的信息流。[官方介绍](https://www.are.na/about) · [Connections](https://help.are.na/docs/getting-started/connections)

对「日式美学」的采用是本提案的设计解释：间隔、节制、材质感和自然阅读秩序。不会把米黄色、书法字体、禅语或文化符号当作充分条件。

## 4. 两条方向与取舍

### A · 人物阅览室（推荐）

主张：**一个值得读的人，是一条可以持续深入的阅读路径。**

- 空间：留白搜索页；一列主阅读区；工具退到侧边或需要时的底部面板。
- 内容：原文观点 → 关键上下文 → 读者问题 → 出处。
- 识别交互：点选一句话，保留原文作为上下文，在旁边或下方打开「前提 / 反例 / 与过去对照」。回去继续读，位置不丢。
- 应避免：静态 PDF、米色模板博客、复杂知识管理工作台。

### B · 人物发现集（保留挑战方案）

主张：**从一条好内容开始，遇见一个值得长期关注的人。**

- 空间：名字搜索与内容预览同屏；移动双列内容流；封面打开为全宽阅读。
- 内容：封面与问题 → 作者 → 完整帖子 → 关注这个人。
- 识别交互：以人物聚类发现内容，跨平台同一篇只出现一次；进入后持续读同一个人的作品。
- 应避免：小红书换色版、封面标题党、无原始图片却强造封面。

### 探索树

```text
目标：低摩擦找到人，并持续获得理解
├─ A 人物阅览室
│  ├─ A1 单列原文阅读 + 按需追问 ← 推荐
│  └─ A2 先展示完整人物档案，再进入阅读 ← 太多前置阅读，退回
└─ B 人物发现集
   ├─ B1 双列发现 + 展开全文 ← 保留可见挑战方案
   └─ B2 一屏一帖强制翻页 ← 长文与评论容易被切断，未深化
```

**两个推荐页面架构都需要区分首次与回访**：首次 Web 默认名字输入；已关注的 iOS 用户默认今日阅读。不能让用户每次回来都重新调研一个人。

### 相对比较（设计判断，非用户实验）

以 A 相对 B 记分：+2 明显更合适，+1 略优，0 未分出，负数倾向 B。不汇成绝对质量分。

| 标准 | A 相对 B | 可验证理由 |
|---|---:|---|
| 5 秒理解下一步 | +1 | A 首页只保留名字输入；B 封面也会吸引点击 |
| 理解内容与追问 | +2 | A 首屏能读到完整观点和问题，B 首屏主要用于选择 |
| 快速发现 | -1 | B 同屏候选更多，适合视觉作者 |
| 去掉 Logo 后的差异 | 0 | 两者仍依赖人物聚合与原文追问交互；仅看配色都不够独特 |
| 无图内容适应性 | +2 | A 长文、短帖、项目更新都成立；B 更依赖封面供应 |
| 真实能力呈现 | +1 | A 容易保留原文、时间与来源；B 需要防止摘要替代原文 |
| 大字与辅助功能 | +1 | A 单列天然容纳更大字号；B 需在大字模式退为单列 |

若目标人群主要关注摄影、穿搭或视频作者，且主要任务是发现，B 可能更合适；若真实测试表明 A 太像普通阅读器，则深化「同一个人跨平台的观点连续性」，不能只加装饰。

## 5. 完整体验：六个场景

### ① 名字输入

首屏一句「今天，想了解谁？」+ 一个输入框 + 进入按钮。支持粘贴已知主页，进阶选项在识别出需要时出现。空白区不塞 Logo 墙、统计、模型列表或能力卡。名字歧义时给简短候选行，用作品和主页区分，不给虚假的置信度百分比。

### ② 调研过程

视觉叙事是「名字变成中心，公开来源逐步汇入，内容整理成可读结果」。最多同时强调两个正在变化的区域。

真实产品将并行角色映射为发现来源、核对归属、读取内容、整理变化，但默认显示对用户有意义的动作与结果；详细活动可展开。显示「找到 4 个候选，2 个仍需确认」，不堆工具名与假思维日志。首批可读内容完成即允许进入；不为了播完动画让用户等待。

允许取消、继续已有结果、单来源重试。同名待确认、来源访问失败与没有新内容是不同状态。原型里的定时器仅用于注明的合成回放，不能进入真实研究状态判断。

### ③ 人物主页

开头控制在一个屏幕内：姓名、简短归属说明、本人介绍、关注按钮、来源可用状态。平台旁写用途（长文 / 作品 / 片段），不只放社交 Logo。

正文分「最近 / 作品 / 观点变化」。后者只对照可引用的历史材料；避免用一篇新帖推断人格或永久立场。长履历、图谱、来源审计进入深入研究，不阻挡消费路径。

### ④ 今日阅读

底部导航为「今日 / 人物 / 留下」；搜索从顶栏进入。默认单列，视觉内容在「发现」里用双列。一张帖子卡只保留：作者 + 来源时间、原文或明确标记的摘要、真实附件、追问/讨论/留下。

| 内容 | 默认呈现 | 展开后 |
|---|---|---|
| 短帖 | 直接给完整短文，无图就无图 | 线程、上下文、评论 |
| 长文 | 标题 + 2–3 行原文或标记过的摘要 | 可读正文、原文定位、选段追问 |
| 图片帖 | 原图保留比例，必要时附短说明 | 图组、文字识别说明、对应讨论 |
| 视频/播客 | 封面 + 时长 + 有出处的关键片段 | 原播放器/跳转、带时间码的字幕与追问 |
| 项目更新 | 变更是什么、原始项目链接 | README/发布记录、前后差异 |
| 转发与重复 | 同一内容合并展示，注明平台副本 | 各版本时间、来源及不同的附加评论 |

不给每条帖子生成大段 AI 摘要，不把 AI 改写伪装成作者原话。默认最新视图尊重时间；深读视图显示入选原因。

### ⑤ 随手追问与评论

先保留原文片段与来源，再选择「前提是什么 / 有什么反例 / 和过去对照」。回答以短段分层，展开才增加推导。基于材料的解释、作者自述、对照推断与未知分开。

评论优先提供有信息增量的片段：作者回应、具体反例、补充证据、未解决的问题。点赞多不能自动代表正确。展示读取范围与截取状态；不把评论人的说法算到作者头上，不把少量片段说成「全网共识」。

每个 AI 回答至少给一个可回原文的出处；不能支持时直接说明缺什么。自由追问沿用当前帖子/选段上下文，切换到全人物研究前明确范围。

### ⑥ 订阅与回访

关注时选择：哪些来源、回看 30/90 天、哪些主题、是否包含评论、每日/每周汇总。抓取频率与通知频率分别管理，不能让「每日推送」暗示「所有平台实时可读」。默认关注公开创作者；不可读来源显示状态。

人物页显示上次成功检查时间、失败来源、暂停与取消入口。跟踪起始时间属于用户自己的关注记录，原帖时间属于内容；旧帖新抓到不冒充刚发布。取消后停止后续调度。

## 6. 不依赖黑箱推荐，也能持续有吸引力

核心循环：**挑选值得关注的人 → 新内容有增量 → 读到一个疑问 → 随手追问 → 留下理解或问题 → 下一次有相关更新时接上。**

稳定内容供给是必要条件。再顺滑的设计也不能保证稀疏更新的人每天都有好内容。没有更新时，给出真实终点，可以主动继续历史专题，但要标记为历史，不假装新内容。

首版规则建议：

1. 「最新」只看用户选定的人与来源，按原始发布时间倒序，保留编辑时间与抓取时间。
2. 同源规范 URL、稳定 post ID 优先去重；相似文本只提示候选重复，避免把不同观点误合并。
3. 「值得深读」由用户开启：保留完整论证/具体案例/实质回应，隐藏重复与已读，每条显示入选理由。AI 的分类可被纠正。
4. 如需作者均衡，作为明确的可选排序：每人先显示一条，其余折叠。不要静默把它混进严格时间序。
5. 新内容到达只显示「有新更新」入口，不让正在读的卡片跳动。返回正文和列表保留位置。

让用户「想继续」的奖励来自观点增量、找到反例、解决旧问题、看懂作者怎么改变。支持流畅滚动、手势返回、预取下一篇；保留可见列表终点与恢复入口，不需要伪造未读或强制连续签到。

衡量是否有效：第一次找到正确人物的成功率；到第一篇有价值内容的时间；有出处的追问完成率；一周后带着同一问题回访的比例；「这次我学到了什么」的用户自述。阅读时长可以记录，但不能单独证明学习感。

## 7. 设计体系

### 颜色与材质

暖纸白 `#FAF9F6`，正文墨色 `#282924`，次级文字 `#66675F`，分隔 `#DDDED5`，操作强调 `#A0442D`，出处链接 `#345949`。正式 token 已写在 [reading.css](reading.css)。

画布不加纸张噪点，颜色由真实内容承担。按钮大多墨色；暖红仅用于选中、聚焦或当前动作。不是复刻 Notion 品牌，也不套小红书红色。

### 字体、空间、内容密度

- 中文界面与正文使用 PingFang / 系统无衬线；宋体只给首页、阅读标题等少量位置。
- 手机正文 17px 左右、行高 1.75–1.95；元信息 12–13px；主要标题 28–34px。Web 阅读列 620–700px。
- 4/8/12/16/24/32/48/72 作为间距节奏。相关元信息聚拢；不同帖子之间留出明显停顿。
- 图片保留比例，不用全局固定卡片高度；功能按钮最小点击区域 44×44。
- 大字模式退单列，允许多行标签；iOS 使用 Dynamic Type 与系统字号，而非把网页像素表直接写死。

### 动效语法

| 动作 | 设计目标 | 建议时长/行为 |
|---|---|---|
| 输入聚焦 | 明确此刻可以输入 | 边线/文字状态 120–160ms |
| 名字提交 | 姓名位置连续地成为人物锚点 | 320–420ms；候选不明确时停在确认态 |
| 来源到达 | 每次新增都能理解来自哪里 | 160–220ms；真实事件驱动，短批次合并 |
| 帖子展开 | 保留封面与原文的空间连续性 | 260–340ms；可被返回手势打断 |
| 追问面板 | 仍看得到正在读的那一句 | 240–320ms；桌面旁栏，手机底部面板 |
| 收藏/关注 | 即时确认动作，可撤销 | 120–180ms；原生端可用一次轻触觉 |
| 新内容到达 | 不打断视野，不跳读 | 顶部提示；点击后再插入 |

时长是设计参数，不是本轮性能测量。原型已实现页面入场、状态回放与面板展开；共享元素过渡、触觉、原生手势和真实事件流仍是后续实现项。

减少动态时取消移动/循环动画，保留静态状态。大量动效应该表现为大量细致反馈，而不是让大量元素同时运动。[Apple Motion](https://developer.apple.com/design/human-interface-guidelines/motion) · [Apple Typography](https://developer.apple.com/design/human-interface-guidelines/typography)

## 8. 需要先统一的数据与状态

本段为提议的扩展边界，不修改现有 canonical report。实施时先做共享契约，再接各渲染器。

| 对象 | 关键字段/关系 |
|---|---|
| Person / IdentityLink | 人物与账号分开；归属依据、状态、撤回依赖 |
| SourceCapability | 能否读资料/正文/评论/历史；最后成功、失败原因、授权与频率限制 |
| Post / SourceVersion | 作者、原 URL、原始/编辑/抓取时间、内容类型、正文定位、附件与版本 |
| PostCluster | 跨平台相同内容、副本差异、可拆开的合并依据 |
| CommentThread | 原帖、评论作者、回复关系、分页覆盖、读取范围 |
| FollowRule | 关注开始/暂停/结束时间、平台、主题、回看窗口、调度与通知偏好 |
| ReadingState | 阅读位置、已读、留下、选段、追问与对应版本 |
| Answer / Claim | 原文片段、来源版本、事实/自述/推断/未知、撤回后的失效关系 |

状态必须设计：零结果、同名、部分结果、不可读取、限流、旧内容、无新更新、重复合并可拆、原文删除、订阅暂停、模型失败、引用失效、离线缓存与同步冲突。

全平台采集和评论覆盖取决于适配器能力与授权，不能把平台图标当成已经接通。最新源码文档与先前记录存在时效差异，本轮未重新验收真实 provider，不宣称运行能力增加。

## 9. 最小交付顺序与验证

1. **选方向。** 用同一份合成内容对比 A/B，验证名字输入、找到正确人物、读一条长观点并追问；记录用户偏好，不用自评高分替代。
2. **打通一个真实内容闭环。** 先用已确认可读的个人网站/RSS/公开项目，完成归属、帖子、版本、去重、时间、出处。未接平台明确不可用。
3. **做阅读留存。** 关注规则、增量刷新、恢复位置、收藏、无更新终点；再验证跨端同步与失效状态。
4. **接带出处的 AI 与评论。** 先单帖/选段，再跨历史对照；评论纳入前检查作者关系与覆盖。
5. **深化原生 iOS。** 用正式 SwiftUI 屏幕替代 HTML 原型，实测动态字号、键盘、VoiceOver、手势、离线与系统返回。

建议方向测试招募 5–8 位实际读者作为第一轮发现问题的样本，不把该数量当统计结论。比较任务完成、理解偏差与主观偏好；只要单列方案让多数目标用户觉得「不想继续读」，就重新审视内容组织，而不是加一层视觉装饰。

最终建议：**A 做日常默认，B 的双列机制留给发现。首页保持名字输入；AI 在内容旁边出现；人物研究能力作为可深入的一层。** 是否喜欢这套审美，仍需你通过可见稿判断。
